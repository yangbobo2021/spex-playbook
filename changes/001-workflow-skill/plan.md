## 实施顺序

1. **验证宿主接入。** 以当前使用的 Codex 客户端为首个验收目标，记录客户端和版本。先用最小编译和运行路径验证三件事：当前会话能与辅助脚本交换请求、原生子 Agent 的角色结果能回到正确的运行时回调、需要用户回答的流程能在下一轮继续。同时核实该客户端能否注册并派发 `/playbook.workflows1` 形式的命令及参数。发现影响已确认行为的接口缺口时，记录复现和影响，按 SDLC 流程修订相应文档。
2. **实现工作流目录。** 以项目内的 `.spex-playbook/workflows/` 为存储位置。每个工作流保留稳定标识、源文件位置或会话正文记录，以及当前成功产物指向。候选产物写入独立编译目录，源文的相对引用仍按原源文目录解析。校验和入口构造均通过后，原子更新当前引用。单测先覆盖空目录、名称歧义、缺失目标和失败后的当前产物。
3. **接入编译。** 由 SLC 管理阶段与校验，Codex 根据阶段请求完成 Agent 工作。从发布包的流程定义加载编译管线，验证注入的解释执行器可以驱动全部阶段。分别呈现澄清问题、阶段错误和成功产物。对候选入口实际构造一次运行实例，核对入口声明、运行时约定及 Playbook / XState 依赖解析。
4. **接入执行和答复。** 将入口的角色声明映射到当前会话或由它创建的原生子 Agent。编译侧和运行侧都使用同一宿主转发机制，沿用宿主权限。工作中需要用户回答时，在运行时允许保存的位置保留 `exportSnapshot()` 的状态与对应产物标识，并把问题带回当前 Codex 会话。用户答复后，用同一运行身份 `restore()` 再交回运行时，保留相应角色的续接信息。对照运行时的终态输出和错误记录呈现结果。
5. **接入 Skill 入口并验收。** 用普通自然语言串起编译、查询、执行和重新编译。首验 Codex 客户端支持目标斜杠形式时，将它接到同一执行入口。完成下面九项验收，并从安装和首次使用走一遍完整用户路径。

## 验证方法与通过条件

自动验证使用 Node.js 的 `node --test`，通过固定的宿主回复检查可重复的行为。在真实 Codex 中复核入口触发、角色调用、用户答复和条件性命令，用会话或工具记录关联实际调用。

| 规格验收项 | 验证方法 | 通过条件 |
| --- | --- | --- |
| 1. 自然语言编译 | 在 Codex 中分别发普通消息，提供完整规程正文和规程文件路径。打开输出位置，再用名称查询。 | 两种输入均触发编译，返回可定位、可执行的产物及可复用的工作流名称。 |
| 2. 编译冲突 | 编译同时要求 VIP 退款直通和大额退款复核的规程，检查澄清内容和工作流目录。 | 问题明确指向 VIP 且金额超过 500 元的重叠场景。本次编译显示待澄清，候选产物没有成为可执行版本。 |
| 3. 查看和定位 | 从空项目开始。随后编译文件来源与正文来源的工作流，再查询列表、指定名称和不存在的名称。 | 空目录与缺失名称各有明确反馈。已有工作流能打开源文件或查到源文记录，以及对应的当前产物。 |
| 4. 重新编译 | 先运行基线，再修改规则并重新编译同名工作流。随后用冲突版编译同名工作流，再以同名和同一输入运行。 | 成功更新后执行体现新规则。冲突版返回澄清或失败，当前引用仍指向最近一次成功产物，后续执行继续体现该产物的规则。 |
| 5. 自然语言执行 | 在另一条普通消息中，以相同的工作流名称分别提交合规订单和有重号的订单，核对可见结果与状态转移。 | 合规订单先核对再复核，返回通过和汇总。重号订单按规程退回并报告问题行。 |
| 6. 目标或输入不明确 | 使用部分名称使其匹配两个工作流，再对明确的工作流省略必需输入。查看是否已有编译或执行请求被派发。 | Codex 分别询问目标或所缺输入，补齐后才发起相应操作。 |
| 7. 运行中提问或失败 | 对需要人工复核的样本记录提问前后状态并答复。另用可重复触发执行错误的样本检查报告。 | 问题出现在原 Codex 会话，答复后从等待位置继续。执行错误报告具体步骤和原因。 |
| 8. 当前宿主承担 Agent 调用 | 在真实 Codex 中各跑一次涉及 Agent 的编译和多角色执行。将 SLC 和 Playbook 请求记录与当次 Codex 会话、原生子 Agent 的工具记录逐项对照。 | 每个 Agent 请求可关联到当前宿主或其原生子 Agent。委派的角色、子 Agent 和返回结果可以相互核对。 |
| 9. 斜杠命令条件 | 记录首验 Codex 客户端、版本、注册与派发验证结果。支持目标形式时，分别用该命令和自然语言传入同一工作流和输入。 | 支持时，两种入口的输入传递、执行规则及结果类型符合规格。宿主缺少能力时，记录依据，且自然语言实跑通过。 |

实现 PR 按九项验收条件记录通过、失败和未验证项，附上产物引用切换前后的证据、代表性执行结果和可核对的宿主调用记录。交维护者审查前，在干净上下文中对照意图、规格和本计划复查 diff，并回放用户路径。

## 实施记录

- 执行快照与回合日志放在工作区之外的本机临时目录。Playbook 会在 Agent 调用前后观察工作区；把回合日志归入项目时，已实测会干扰同项目的另一轮执行。产物仍保存到项目目录，仓库增加生成产物与验收证据的忽略规则。
- SLC 0.22.0 的无角色 schema-3 产物可能带旧式注册包装。执行端检查链接工厂声明的 schema，并在这个场景中用链接工厂构造运行实例。包含角色的 schema-3 产物沿用生成的注册入口。
- 编译接入 SLC 自带的机械校验纠正流程。产物需要修正时，校验结果通过同一桥接交给当前宿主继续处理。
- Git 项目使用 Playbook 的正式工作树协调锁。当前 Codex 权限拒绝这一写入时，执行端保留原仓库身份并报告发生问题的步骤。中断的答复回合保留运行记录，提示用户核对已产生的操作后重新开始。
- 更新 `AGENTS.md`，清理初始化阶段的临时说明。开发流程约定沿用。
